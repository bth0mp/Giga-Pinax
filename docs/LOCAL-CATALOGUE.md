# Bundled reference data

The extension includes derived type databases for six of the American Numismatic Society's type series, each converted from that series' own public `nomisma.rdf` export by `scripts/import_rdf.py`. Every one of them, and each derived database here, is available under the [Open Database License 1.0](https://opendatacommons.org/licenses/odbl/1-0/). Monograms, symbols, images and auction results are excluded from all of them.

| Corpus | Source | Export | Bundled | Left out |
| --- | --- | ---: | ---: | --- |
| OCRE (RIC) | [numismatics.org/ocre](https://numismatics.org/ocre/) | `nomisma.rdf`, 127,151,792 bytes | 52,254 active types, 2,808 redirects | 1,050 ambiguous replacement chains, 1 conflicting record |
| CRRO (RRC) | [numismatics.org/crro](https://numismatics.org/crro/) | `crro.rdf`, 4,922,384 bytes | all 2,602 RRC types | nothing |
| PELLA (Price) | [numismatics.org/pella](https://numismatics.org/pella/) | `pella.rdf`, 22,154,165 bytes | 4,573 Price types | 2,274 Le Rider die combinations, 382 PELLA type numbers |
| SCO (Seleucid Coins) | [numismatics.org/sco](https://numismatics.org/sco/) | `sco.rdf`, 23,373,517 bytes | all 8,694 types | nothing |
| PCO (Lorber, CPE) | [numismatics.org/pco](https://numismatics.org/pco/) | `pco.rdf`, 7,334,635 bytes | all 1,691 CPE types, and PCO's 1,067 links from a Svoronos number to the CPE type it became | 1,959 Svoronos records |
| AGCO (Newell, Demetrius Poliorcetes) | [numismatics.org/agco](https://numismatics.org/agco/) | `agco.rdf`, 484,052 bytes | all 182 types | nothing |

All six exports were retrieved on 24 September 2026; each `metadata.json` records its file's SHA-256 and byte size.

**BIGR (Bopearachchi) is not bundled and still goes online.** A Bopearachchi reference is resolved by searching BIGR and verifying every hit against the Bopearachchi citation in the hit's NUDS XML, because BIGR numbers its own types differently from Bopearachchi's series ("Euthydemus I 13.1" against "Euthydème I 24A"). That citation is in the NUDS records only: none of the 2,109 `nmo:TypeSeriesItem` records in `bigr.rdf` carries it, and the file's 910 mentions of Bopearachchi are all monogram labels. Nothing in the export can tell "Bop 24A" from "Bop 24", so bundling it could only answer with a record nobody verified. The corpus stays online until the export carries the citation.

PCO publishes two catalogues: Catharine Lorber's *Coins of the Ptolemaic Empire*, volume I (CPE), which it indexes — part 1's types as `cpe.1_1.330`, titled "Coins of the Ptolemaic Empire Vol. I, Part 1, no. 330", and part 2's bronzes under Lorber's B numbers as `cpe.1_2.B549`, titled "… Part II, no. B549" — and Svoronos's older numbers as `svoronos-1904.*`. A CPE reference is read as `CPE 330`, `CPE B549`, `CPE I 330`, `CPE no. 330` or `Lorber CPE 330`, typed or in lot text (and typed as PCO's own titles, which a Recent chip carries), and names its record outright: the number alone says the part. A letter after the number is part of it and keeps its case, because PCO holds both `cpe.1_1.506A` and `cpe.1_1.506a`. A volume PCO does not publish (`CPE II 330`) is left unread and searched for prices, as every CPE citation was before. A CPE number past the end of the volume PCO holds (`CPE 1712`) is still read as a CPE citation — the key names every volume of Lorber's book, and nothing in the export says where a later volume's numbers end — so the package has no card for it, numismatics.org answers that it has no such record, and the citation is searched on acsearch with the same phrase, `"CPE 1712"`, as before. No Svoronos record is bundled as a card of its own. PCO replaces 1,067 of them with the CPE type each became (`dcterms:isReplacedBy`, with the same target as its `skos:exactMatch`; every one names exactly one type), and those links are kept, 38,789 bytes of them, as `concordance` in `pco/metadata.json`; a link is written only when every type it names is bundled. A Svoronos citation on its own (`Svoronos 487`, typed or a row of lot text) is still searched for prices as before, and where PCO links the number the card is the CPE type it became, from the package, with the line "Svoronos 487 is filed in PCO as CPE 330."; a number linked to several types would offer them all and open none. A Svoronos number with no link, a letter PCO does not write, or a citation with anything else beside it stays the prices-only card it always was. AGCO publishes Edward T. Newell's *The Coinages of Demetrius Poliorcetes* and nothing else, titled "Newell Demetrius Poliorcetes, no. 45" (`newell.demetrius.45`). Newell wrote several catalogues that dealers cite by number — among them the Seleucid mints and the Alexander coinages of Sidon, Ake and Tyre as well as Demetrius — so a bare `Newell 45` cannot say which book it means and stays prices only. A reference is read only where it names Demetrius — `Newell Demetrius 45`, `Newell, Demetrius 45`, `Newell Demetrius Poliorcetes, no. 45`, typed or in lot text; its acsearch term also requires the king's name, `Demetrius` or `Demetrios`, in the lot.

PELLA leaves out the type series no reference the extension reads can cite: `SIMPLE_REFERENCE` reads a Price number and nothing else, so `lerider.*` and `pella.*` records could never be reached. `metadata.json` records that count, the per-group breakdown and the reason. All 184 replacement links between type records in the PELLA export run from a Le Rider record to a PELLA one, so no redirect between bundled records exists. CRRO and SCO carry none between type records either: CRRO's export has no replacement link at all, and all 1,293 of SCO's run between monograms, which are not bundled.

## Coverage and provenance

Each export contains type records and their side descriptions. Individual museum specimens are separate datasets linked to those types; they are not imported. The Type link on a card opens the corpus's own page for exploring linked examples. There are no auction results or coin images in any of these files. No dataset publication date is published for any of them. `generatedOn` records when the compact files were made, not when the source data was published or last corrected.

SCO identifies the types of both parts of Seleucid Coins under `sc.1`, which is the identifier `lookup.js` already builds from an SC reference; each record's title names the part it belongs to ("Seleucid Coins (part 2) 1315.3c" is `sc.1.1315.3c`). CRRO identifiers are not always the title in lower case — "RRC 98B" is `rrc-98b` — so a reference is matched against the titles rather than turned into an identifier.

Each `extension/data/<corpus>/metadata.json` identifies its source SHA-256, byte size, record counts, replacement handling and generated files, and a corpus bundled in part also carries the count it left out and why. A shard name such as `records-1(2).json` is the RIC second-edition volume's own key, not a duplicate download: the parenthesised number is part of the identifier prefix the records carry. CRRO, PELLA, SCO, PCO and AGCO have no volumes to file their records under, so each of them is one group named after its identifier prefix — `records-rrc.json`, `records-price.json`, `records-sc.json`, `records-cpe.json`, `records-newell.json` — and would split into lettered parts by the same rule if it ever passed the cap. Source identifiers retain their exact case. Explicit replacement links are followed only when they resolve to an available canonical record. Unresolved or cyclic replacements do not produce an invented active card. Conflicting repeated records or side descriptions are withheld and recorded in the metadata; affected references can use the online fallback.

No generated file may exceed 4 MiB, because Mozilla's add-on linter rejects any non-binary file of 5 MiB or more. A group whose records pass that cap is split by identifier order into evenly sized lettered parts — `records-5.a.json` and `records-5.b.json` for RIC V — and the metadata lists each volume's parts with the identifier each one starts at, so a lookup by identifier still opens exactly one file without reading the index. The importer measures every generated file before it writes the first one, so a bundle the cap refuses leaves the data directory exactly as it was. A volume cannot be split past `records-5.z.json`: the importer, the build and the extension all refuse more parts than there are letters to name them.

`numbers.json` is OCRE's alone, and the importer's corpus table is what says so. It maps the leading integer of each title's RIC number to the positions in `index.json` that carry it, so a lookup for RIC 972 reads a few dozen titles rather than all 52,254. The other five corpora need no such index: a Crawford or Price reference is compared with whole titles, and an SC, CPE or Newell reference names its record outright, so nothing parses a number out of a title for them. It is derived from the index and never a source of its own: `tests/local-catalogue-index.test.mjs` checks every bundled title against the reference parser the lookup uses, and checks that the listed entries answer every shape of reference exactly as a scan of the whole index does. It records the number of index entries it was built from: a reader that finds a different number of entries treats the bundle as unavailable rather than answering from a stale file, and `scripts/build.py` recomputes the whole index with the importer's own function and refuses to package a bundle that disagrees.

RDF values preserve multiple authorities, denominations, materials and mints. A value the export states as uncertain is a blank node with no identifier of its own, in the RDF and in the JSON-LD alike, so neither the local card nor the online card names it.

Nomisma concept labels and classes are absent from every one of these exports, so the names travel with the package in a file of their own. `extension/data/nomisma-labels.json` is slug to English label and nothing else, for every Nomisma concept any bundled record names in a field a card shows — authority or issuer, denomination, mint, material and portrait. It is generated from the tracked snapshot `scripts/data/nomisma-labels.json`, which holds the endpoint, the query text, the retrieval date, the licence and the whole fetched result. `extension/data/NOTICE.txt` attributes it. Nomisma publishes its concepts under [CC BY 3.0](https://creativecommons.org/licenses/by/3.0/), so the derived label file is CC BY 3.0 while the type records beside it stay ODbL.

Of the 1,622 concepts the six bundles name, 1,620 carry an English preferred label; `dupondius_or_as` and `uncertain_74_sco` have none and are absent from the generated file, so a card shows those two identifiers as they are. Nothing is guessed and nothing is title-cased into a label nobody published.

A field the export gives more than one value is left off the local card rather than one of them being chosen: `labelFor` names a field only where the record holds exactly one identifier for it, so a type with two authorities, or a denomination recorded two ways, shows no authority or no denomination at all. It is not rare — 569 of the 15,869 records in CRRO, PELLA and SCO, 36 of PCO's 1,691 and 8,904 of OCRE's 52,254 carry at least one such field (none of AGCO's 182 does), almost all of them two authorities or two denominations. The online card is less careful: `toCard` takes the first value of each field, so **Check online** names one of them, and the **Type** link on every card opens the record itself, which lists them all.

Three sources can name a concept on a local card, in this order: the runtime label cache that an online Nomisma lookup filled, because that is the record's own publisher answering now; `ric-people.js`, for an OCRE authority or portrait; then the bundled labels. `ric-people.js` is read for OCRE alone — it was filtered against OCRE's own concepts — and it takes precedence over the bundled label file, so a ruler name on a RIC card is the one the Nomisma snapshot in `ric-people.js` carries. As it happens the two agree about all 214 people, so the order decides nothing today and is kept because the snapshot is the narrower, checked list. An identifier none of the three names stays an identifier.

The label file is read lazily, once, the first time a card is built, and never for a lookup that misses. A missing or damaged one costs a card its names and never its answer: the record is still the record, with the identifiers on it, and the lookup is never reported as unavailable because of it. `tests/local-catalogue.test.mjs` compares the local card with `toCard` over the same record's JSON-LD, field by field, with the labels the package carries and with a cache that overrides them, and they are equal either way.

`ric-people.js` includes the 214 concepts that Nomisma classifies as `foaf:Person`; it excludes 58 deities, personifications, groups and other concepts. Canonical names are English preferred labels. English and Latin preferred or alternate labels are search aliases. `catalogues.js` adds the spellings a European lot heading writes and no label carries: the regular endings of an English -ian name (Latin -ianus, Italian and Spanish -iano, French -ien, so "Vespasiano" and "Aurélien"; Trajan's -jan gives "Traianus", "Trajanus", "Traiano" and "Trajano"), and a closed table, `EXTRA_SPELLINGS`, of Latin, German, French, Italian and Spanish spellings of RIC I–V rulers ("Nerón", "Nerone", "Adriano", "Augusto", "Cómodo", "Antonino Pío", "Faustina Minor", "Philippus I", "Elagabal", "Konstantin I"), each mapped to a person Nomisma already names. No spelling adds a person, and none is anybody else's name, alias, section or mint. One rule in `lot.js` follows RIC's filing rather than a spelling: RIC I² heads no section with Octavian and lists his coins under Augustus, so a lot heading naming Octavian ("Octavian as Augustus, 27 BC – 14 AD") asks for Augustus beside him; Octavian keeps his own name, and no other ruler is widened. A title is no ruler, in English or as the Spanish and Italian houses write it: "as Augustus", "como Augusto", "come Cesare". Missing legends, descriptions and dates remain absent.

The same generated module carries the modern names Nomisma and Wikidata give a RIC VI–IX mint section, so a typed "Trier" reaches RIC's **Treveri**, a typed "Arles" reaches **Arelate** and a typed "Sofia" reaches **Serdica**. Two sources, because Nomisma's mint concepts carry `skos:closeMatch` and `skos:exactMatch` links to the same place elsewhere, and one of those places is Wikidata: the tracked snapshot records every such link, the importer follows the Wikidata ones and nothing else, and the labels and aliases it brings back are weighed by the same rules as Nomisma's own. Three kinds of label are taken from either source, and no fourth: every label in the language of the country the mint stands in today, because a country spells the place it holds as the place; every English label, because that is the language the extension is read in; and a Latin-script spelling that at least two of English, French, German, Italian and Spanish share once it is folded and stripped of its diacritics, which is the exonym those languages have in common rather than one language's own word (Italian alone calls Lugdunum "Lione" and Cyzicus "Cizico"). The language is chosen per mint by hand, in `MINT_COUNTRY_LANGUAGE` in `scripts/import_people.py`, with the town and country named beside each one; a mint concept missing from that table stops a regeneration rather than quietly losing its name. Several of those languages are written in a script the extension can never match — Arabic for Alexandria and Carthage, Bulgarian for Serdica, Greek for Thessalonica, Serbian Cyrillic for Sirmium — and nothing is transliterated out of them; where the second source writes the same name in Latin script, as Wikidata writes Serdica's "Sofia" in English and in every exonym language, that spelling is reached after all. Of a Wikidata item the snapshot keeps its labels and aliases, the classes its `P31` says it is an instance of, and the targets of three statements — `P1366`, `P276` and `P131` — and nothing else: no description, no sitelink and no other statement is even written into it.

Those three statements are there because four of the mints could not be reached without them. Nomisma links Londinium, Lugdunum, Mediolanum and Ticinum to the **Roman** city rather than to the town standing there now — Q927198, Q665, Q729978 and Q28215083 — and every language kept titles those by the Latin name, so "London", "Lyon", "Milan" and "Pavia" are in no label of them. Each of those items does publish a statement naming the modern town, and the importer follows **one hop and no more**, by a precedence rather than a property chosen per mint: the first of `P1366` (replaced by), `P276` (location) and `P131` (located in the administrative territorial entity) the item carries is the only one read, and nothing falls through to the next. Two things stop the hop before a request is made: a statement naming several places at once, which is an administrative chain rather than a place (Rome's item lists nine parents, Arles four); and `P131` on an item that is already a present-day settlement, whose administrative parent is its county or its province and never its own name. What the hop reaches is used only when that item's own `P31` says it is a populated place — one of the town, city, commune, municipality and metropolis classes listed in `SETTLEMENT_CLASSES` in `scripts/import_people.py`, and none of the country, region, province and administrative-division classes in `REGION_CLASSES` beside it. Its names are then weighed by the same three rules as every other, so a town is reached by what it is called and not by what it is. Of the twenty-two linked items, ten name a place to go to; eight of those ten are towns, and the two that are not were fetched and refused by their own classes — Carthage's item leads to the Exarchate of Africa, a Byzantine province, and Ostia's to the Lido di Ostia, a frazione and a seaside resort. A name a mint's own item publishes outranks one another mint was hopped to, so Ostia's parent, which is the city of Rome, could not cost Rome the name "Roma".

A mint alias resolves a section and never a ruler. A spelling that is also a ruler's name, or that carries one inside it as a whole word, is dropped rather than left to choose between a place and a man; so is a spelling two mints share, one that is another mint's own RIC section, and one that is an ordinary English word ("Rim" and "Rom" are what Croatian, German and Danish call Rome, and both are English words; "Rome" itself is kept, because RIC heads a section with it). The ruler spellings are the ones the same run generates, so the two tables cannot drift apart.

Wikidata also lists, beside a city's names, things that are not one, and those are refused by concept in `NOT_A_NAME` in `scripts/import_people.py`, each with the reason beside it: the title of an encyclopaedia article about the place ("history of Pavia"); a nickname ("the Eternal City", "Caput Mundi", "Pearl of the Mediterranean", "capitale des Gaules"); a whole different place (Longpré-lès-Amiens is a commune of its own); and an abbreviation or a title, which is what London's item adds ("LDN", "Lon.", "Lond.", and "Augusta", an honorific several cities and several empresses carry). A nickname has to go because a heading naming no ruler is read for the earliest mint spelling in it, so a Trier coin sold with a line of prose about the Eternal City would have been filed under Rome. An alias of one or two characters is a code rather than a name — Wikidata lists "RM", Rome's Italian province code — and is dropped as a class.

Of the 21 mint concepts in the tracked snapshots, 20 carry a modern name that differs from the section RIC files them under. Twenty of the 21 link to a Wikidata item — Thessalonica is the one that links to none, and keeps the names Nomisma itself publishes — and Ticinum and Treveri link to two apiece. The one left with nothing is Aquileia, which already is the name on the map.

**"London", "Lyon", "Milan", "Pavia" and "Trier" all reach their Latin section**, four of them through the one statement hop: `Q927198 P276 → Q84` London, `Q665 P1366 → Q456` Lyon, `Q729978 P1366 → Q490` Milan and `Q28215083 P131 → Q6259` Pavia, with Trier reached by Nomisma's own label as before. Cyzicus and Nicomedia came with them: `Q615449 P131 → Q177298` gives **Erdek** and `Q209349 P1366 → Q129649` gives **İzmit**, the towns those two mints stand in today. **"Lyons" is the one name of the five that is still not recognised**, and this is a limit of the source rather than an oversight: Wikidata publishes "Lyons" as a name of Q456 in no language kept — not as an English alias, not anywhere in either tracked file — and nothing is invented to answer for it. A lot written "Lyons" is still looked up by RIC's own spelling, which reaches Lugdunum.

A lot heading that names a mint and nobody else ("Londinium. RIC 12", "Arles mint") is read as that mint's section, with the volumes the section implies. Its coins are offered and never opened: a heading is ruler-less wherever the people table lacks its spelling, so a section read from its mint alone never picks one emperor's coin as the answer. A mint typed with no volume ("RIC 411 (Rome)", "RIC Rome 411") is offered the same way, and one typed with its volume ("RIC VII Trier 12") opens its coin. A mint a lot writes in brackets after a number with no volume ("Probus. Antoninianus. RIC 40 (Ticinum).") keeps the heading's ruler beside it: his coin at that mint opens, unless one of his own sections also holds the number, when both are offered, and otherwise his own coins with the number are offered. A heading that names a ruler as well is the ruler's, exactly as before: the mint only says where the coin was struck, and a ruler volume's number would otherwise be thrown away for it. Every mint the heading names behind the ruler still travels with the row as where the coin may have been struck. A mint word in front of the ruler is the house's category or name ("Rome Roman Empire. Diocletian. …", "London Coins Auction 180. …"), a place with a hoard or a find behind it or "found near" in front of it ("the Lyon hoard", "Found near London") is where the coin was found, and the city a commemorative honours ("Urbs Roma", "Constantinopolis commemorative") is not read as a mint at all; none of them travels: when the ruler's only coin with that number is at a RIC VI–IX mint none of them names ("Constantius I. Follis. Trier. RIC VI 12." finds only his Alexandria 12), it is offered and never opened, locally and online; at the mint the heading names it opens as before. Where the ruler has the number at several mints and one of them is the mint the heading names ("Constantine I. Follis, Treveri. RIC VII 42.", his coin at fourteen mints), the bundled catalogue keeps only his coins of that mint and those filed under his own name, and one left opens: the ruler and the mint both agree. A heading naming two mints narrows the same way, but what is left is offered, since one of the two may be a category rather than the mint. A volume a lot or a typed reference names without its edition ("Nero. RIC I 306", "Hadrian. RIC II.3 2140", "RIC I Nero 306") never opens a type, even where OCRE holds that volume in its second edition alone (RIC I, II.1 and II.3, read from the volume list, never from a list of numerals): the citation may be the first edition's number, which names another coin. Where the bundle holds one type for it, that type is offered alone, named as a collector writes it and with the reason ("RIC I² Nero 306 — the lot says RIC I without an edition; the second edition is the one bundled"). Written with its edition ("RIC I² Nero 306"), it opens as before. The mint never joins the rulers a lot row carries, so nothing asks OCRE's portrait facet for a place.

The people concept snapshot was retrieved on 15 September 2026 with one request to Nomisma's documented [`getRdf` aggregate API](https://nomisma.org/documentation/apis/), rather than one request per identifier. Its SHA-256 is `0619ff8f2bd3d1c6fc58d08a3cc77a5dce443631fad2cb81f42375198675253e`. The generated module records the endpoint, snapshot hash, generation date and inclusion counts, and beside them the two sources the mint aliases came from and Wikidata's [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/) dedication: the ruler names are Nomisma's under [CC BY 3.0](https://creativecommons.org/licenses/by/3.0/), the mint aliases are Nomisma's and Wikidata's together, and each licence travels in the file that carries the data. Volume membership is derived from active OCRE authority and obverse-portrait links; it helps suggest searches but does not alter RIC's catalogue sections or claim that every source link is historically correct.

## Runtime

Each corpus is loaded on its own and only when it is asked about: a popup that has just opened reads nothing, a Bopearachchi reference reads nothing, and a Price lookup never touches OCRE's files. A reference that names its record outright — `SC 1266.2` is `sc.1.1266.2`, `CPE B549` is `cpe.1_2.B549`, `Newell Demetrius 45` is `newell.demetrius.45` — opens the record from the metadata and one shard, without reading an index at all. A RIC reference reads the number index and the searchable index; a Crawford or Price reference reads the searchable index with the metadata beside it and is matched against whole titles, first as an exact title and then against the near misses of its own group, through the same `pickMatch` and `inGroup` rules the online search results go through. The metadata is read with the index because its record count is the one thing that tells the index the importer wrote from a stale one whose every title still resolves; a disagreement between the two, or metadata that cannot be read, is `unavailable` rather than a miss. Each file is read once per window and kept: the index entries a lookup compares are built as it first reaches them — a RIC lookup builds only the entries `numbers.json` lists for its number, and a title catalogue builds its list once — and OCRE's titles are read as references once each, so a lookup that broadens its volume or section, or a second lookup in the same window, reads nothing again.

An exact title opens that record. A handful of near misses — up to five in the reference's own group — are offered as **Did you mean**, exactly as the online search offers them, and the lookup does not go online for them. A CPE or Newell number the bundle lacks offers the records that carry its number bare or with a letter after it — `CPE 466a` offers `cpe.1_1.466`, `466A` and `466B`, never `4660` — and online, where the lookup goes when the bundle has nothing to offer, the record the number names is fetched and a missing one is a clean miss: nothing is known about what a PCO or AGCO search returns for a number, so none is made. For SCO those candidates are deliberately a superset of the online ones: `SC 1266.9` offers `sc.1.1266` and `sc.1.1266.2`, where ANS's own search for the base number returns `sc.1.1266` alone, though `sc.1.1266.2` is a real record of that group. They are choices the collector makes, never a record opened for him. Anything short of an exact answer or a candidate list is a local miss, and the lookup falls back online rather than reporting that the type does not exist. Local lookups require neither a network service nor ANS permission, and a local card names no concept over the network: the names are in the package. Missing data can use the existing online provider with access, and the explicit **Check online** action can request that access. Results describe their bundled source; an absent local match does not establish that a type does not exist.

acsearch price research is separate and still needs internet access and the collector's provider session. There are no auction-price records in this database. Bundled files do not modify personal collection records or enter backups. Data updates arrive with extension releases.

## Rebuilding the data

The developer converter is `scripts/import_rdf.py`. It uses Python's standard library and never downloads an export: the export is a file you already have. Its `--fetch-labels` option, and the same label step inside `--refresh` (below), are the only things here that use the network, and they read Nomisma's SPARQL endpoint, not an export. From the repository root:

```powershell
python scripts/import_rdf.py "Numismatics.org RDF/nomisma.rdf" extension/data/ocre --generated-on 2026-09-14
python scripts/import_rdf.py --corpus crro "Numismatics.org RDF/crro.rdf" extension/data/crro --generated-on 2026-09-17
python scripts/import_rdf.py --corpus pella "Numismatics.org RDF/pella.rdf" extension/data/pella --generated-on 2026-09-17
python scripts/import_rdf.py --corpus sco "Numismatics.org RDF/sco.rdf" extension/data/sco --generated-on 2026-09-17
python scripts/import_rdf.py --corpus pco "Numismatics.org RDF/pco.rdf" extension/data/pco --generated-on 2026-09-24
python scripts/import_rdf.py --corpus agco "Numismatics.org RDF/agco.rdf" extension/data/agco --generated-on 2026-09-24
python scripts/import_people.py generate extension/data/ocre scripts/data/nomisma-ocre-concepts.rdf extension/ric-people.js --mints scripts/data/nomisma-mints.json --wikidata scripts/data/wikidata-mints.json --generated-on 2026-09-18
python scripts/import_rdf.py --write-labels
python scripts/build.py
```

`--corpus` defaults to `ocre`. Each corpus's export is at `https://numismatics.org/<corpus>/nomisma.rdf`; the importer never downloads one. `NOTICE.txt` is written by hand and the importer leaves it alone.

Use the actual conversion date when producing a new snapshot. To deliberately refresh the checked-in Nomisma snapshot, make one aggregate request before generation:

```powershell
python scripts/import_people.py fetch extension/data/ocre scripts/data/nomisma-ocre-concepts.rdf
```

The mint snapshot is refreshed the same way, one request per RIC VI-IX mint concept. It is saved with each concept's source URL, its labels, the `skos:closeMatch` and `skos:exactMatch` links it carries, the retrieval date and the licence, and the build reads that file and never the network:

```powershell
python scripts/import_people.py fetch-mints extension/data/ocre scripts/data/nomisma-mints.json --retrieved-on 2026-09-18
```

The Wikidata snapshot is refreshed from that file and from nothing else: the `matches` links in it decide which items are asked for, one request each, under the same User-Agent. Each of those items is saved with its labels and aliases, its `P31` classes and its `P1366`, `P276` and `P131` targets; the run then follows one hop from each, at most one item per linked item, and fetches those too — 22 items and the 10 they lead to, 32 requests in all. A mint linking to no Wikidata item is named in the run's own output rather than passed over in silence, and every hop it follows is printed as `Q665 P1366 -> Q456`, so the file can be checked against the run that wrote it. Wikidata dedicates its structured data to the public domain under CC0 1.0, and the snapshot, `extension/data/NOTICE.txt` and the generated `extension/ric-people.js` header all say so:

```powershell
python scripts/import_people.py fetch-wikidata scripts/data/nomisma-mints.json scripts/data/wikidata-mints.json --retrieved-on 2026-09-18
```

Both mint snapshots travel together: a regeneration stops if the Wikidata one no longer holds an item the Nomisma one links to, or the town one of those items leads to, rather than losing those names without saying so.

The concept labels are refreshed the same way, from the bundled records themselves. `--fetch-labels` collects every concept the records name and asks Nomisma's SPARQL endpoint for their English preferred labels, in batches of 320 identifiers given as a `VALUES` list — six requests for the 1,622 concepts the six bundles name, under the same User-Agent `import_people.py` uses. `--write-labels` then rewrites `extension/data/nomisma-labels.json` from that snapshot and the records, with no network at all, and is what `scripts/build.py` checks the committed file against:

```powershell
python scripts/import_rdf.py --fetch-labels --retrieved-on 2026-09-24
python scripts/import_rdf.py --write-labels
```

Without the exports — which is what a contributor or a CI run has — the shards, the index, the number index and the shard map are rebuilt from the committed JSON alone, through the same code the full import writes its files with:

```powershell
python scripts/import_rdf.py --reindex extension/data/ocre
python scripts/import_rdf.py --reindex extension/data/crro
python scripts/import_rdf.py --reindex extension/data/pella
python scripts/import_rdf.py --reindex extension/data/sco
python scripts/import_rdf.py --reindex extension/data/pco
python scripts/import_rdf.py --reindex extension/data/agco
```

It reads the records back out of the shards the metadata names, takes the corpus from that metadata rather than from the command line, refuses a directory that is short of the records the metadata counts, and writes byte-identical files to the ones the full import produces. It cannot change a record, only how the records are indexed and divided into files. `python scripts/build.py` runs the same rebuild over every corpus directory before it packages anything and refuses a bundle whose generated files are not the ones the importer would write today.

The raw ANS source folder is ignored by Git; the compact data, filtered Nomisma snapshot and converters are committed so release builds need neither the exports nor network access. End users only install or reload the extension.

### The monthly refresh

`.github/workflows/refresh-data.yml` does all of the above on a schedule — at 04:17 UTC on the 3rd of every month — and whenever it is started by hand from the repository's **Actions** tab (**Refresh bundled data** → **Run workflow**). It never pushes to `main`; what it finds is proposed as a pull request for a person to review and merge.

It runs as two jobs. The first can only read the repository. It asks the importer which exports there are (`python scripts/import_rdf.py --list-exports`) and downloads each with `curl --fail`, retrying four times a minute apart; a download that still fails — numismatics.org answers 503 now and then — fails the job, and no pull request is opened. It then runs `python scripts/import_rdf.py --refresh exports --generated-on <today> --report refresh-report.json`, which checks that every export is there, and hashes it, before it writes anything, imports again only the corpora whose export differs from the one their `metadata.json` records (by SHA-256 and byte size), so an unchanged corpus keeps its files and its generation date, and fetches the Nomisma labels through the same query and request budget as `--fetch-labels`, rewriting the tracked snapshot only when Nomisma's answer differs. An OCRE import regenerates `extension/ric-people.js` from the tracked people and mint snapshots, without the network. When anything changed, both test suites and the build run over the new data, and the job hands on the change as a patch together with the text of the pull request: which corpora were imported again, whether the labels changed, and a table of each corpus's record, active-type and redirect counts before and after.

The second job is the only one that can write — `contents: write` and `pull-requests: write`, granted in this workflow alone — and runs none of the repository's code: it first refuses a patch that touches any path the importer does not write (anything but `extension/data/`, `extension/ric-people.js` and `scripts/data/nomisma-labels.json`), or that renames a file, adds a symbolic link or makes a file executable, and fails rather than apply a patch it cannot read; then it applies the patch to a new `data-refresh/<date>-<run>` branch, pushes that branch and opens the pull request against `main`. The pull request's checklist names what the workflow does not do: the hand-written `NOTICE.txt` retrieval dates, the counts in this document, the README and the store listing, the changelog line, and the Firefox lint, since a pull request opened with the workflow's own token starts no other workflow. The repository must allow GitHub Actions to create pull requests (**Settings** → **Actions** → **General** → **Workflow permissions**) for that last step to succeed.
